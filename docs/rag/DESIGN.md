# 設計

## 1. 現状（2026-10-13 調査）

```
parkhomes-okinawa.com/QAparkhome/
  └ iframe → hideo-t.github.io/QAparkhome/（このリポジトリの index.html）
        ├ qa_data.json（3MB）をブラウザで全部読む
        ├ バイグラム＋キーワード一致で上位8件を選ぶ
        ├ system プロンプトをブラウザで組み立てる
        └ POST https://aisdr-proxy.hdxrope.workers.dev/  { model, system, messages }
              └ Anthropic Messages API（APIキーは Worker の Secret）
```

### 課題

| # | 課題 | 根拠 |
|---|---|---|
| A | 知識の中身が薄い | `qa_data.json` 8,100件のうち、違う回答は50件だけ。残りは「〜について教えて」「〜 知りたい」等の言い換えの水増し。「質問1」形式のダミー質問が150件ある |
| B | 検索が表面の文字一致 | 言い回しが違うと拾えない。水増し・ダミーが上位を占めうる |
| C | Worker の防御が弱い | 用途の固定・利用元の制限・回数制限がない。詳細は private の aisdr-proxy リポジトリに記録 |
| D | 回答の根拠が見えない | 出典表示はカテゴリ名のチップだけ |
| E | 品質を測る手段がない | 評価セットも運用ログもない |

## 2. 目標の構成

```
ブラウザ（index.html）
  └ POST https://aisdr-proxy.hdxrope.workers.dev/parkhomes/chat  { messages }
        Worker（専用ルート）
        ├ Origin 許可リスト（parkhomes-okinawa.com / hideo-t.github.io / localhost）
        ├ IP 単位のレート制限（Workers Rate Limiting）
        ├ 入力の上限（履歴10往復・1発言1000字）
        ├ system = 固定の指示 ＋ 知識ベース全量（cache_control でキャッシュ）
        ├ model・max_tokens はサーバー側で固定
        └ Anthropic Messages API
        → { answer, model, usage }
```

## 3. 設計判断

### 3.1 新しい Worker を立てず、共用 Worker に専用ルートを足す

- 共用の `aisdr-proxy` は「AIの町医者」も `/` `/openai-image` `/deepseek` を使っている。
  `/` 自体を締めると町医者が壊れるおそれがある（町医者の配信元を把握していない）。
- 別 Worker にすると APIキーの Secret を二重に登録・管理することになる。
- そこで `aisdr-proxy` に **Park Homes 専用ルート `/parkhomes/chat`** を足し、コードは
  `src/parkhomes.js` に分ける。既存ルートの挙動は変えない。
- 段階5で D1・Vectorize などを足して共用 Worker が重くなったら、別 Worker へ切り出す。

### 3.2 `/` の防御は段階的に

- QAparkhome を新ルートへ移した後、`/` の利用者は町医者だけになる。
- 町医者の配信元（Origin）が分かれば `/` にも許可リストをかける。分かるまでは触らない。
  → PLAN.md の 1c。

### 3.3 検索をやめて知識ベースを全部渡す（段階2のA案。段階1で先行導入）

- 元の50問は約4,300字（数千トークン）しかない。検索で8件に絞る理由がない。
- 全量を system に入れ、`cache_control` でキャッシュする。
  Claude Sonnet 5 のキャッシュ最小長は 1,024 トークンで、これを超える。
- 検索漏れがゼロになり、水増しデータの悪影響も消える。
- カタログやPDFを足して数十万トークン規模になったら、段階5でベクトル検索に切り替える。

### 3.4 モデル

- 段階1では今と同じ `claude-sonnet-5` をサーバー側で固定する（挙動を変えないため）。
- `claude-sonnet-5-5` や `claude-haiku-5-5` への切り替えは、段階4の評価セットで比べてから決める。
- `claude-sonnet-5` は応答の先頭に `thinking` ブロックを付けることがある。
  Worker 側で `type === "text"` のブロックだけを連結して `answer` として返す。

### 3.5 レート制限の値

- Workers Rate Limiting の binding を使う。窓は 10秒か60秒しか選べない。
- 1 IP あたり 60秒に10回。人が会話する速さでは当たらず、機械的な連打は止まる。
- この制限は Cloudflare の拠点ごとに数える近似値。厳密な上限ではない。
  料金の最後の歯止めは Anthropic コンソール側の月額上限で持つ。

### 3.6 Origin チェックの限界

- Origin はブラウザ以外からは偽装できる。Origin チェックは「他サイトに埋め込まれて使われる」ことを防ぐもので、
  直接叩く攻撃はレート制限と「system を受け付けない（用途を Park Homes の回答に固定）」で抑える。

## 4. 知識ベースv2（段階2）

- 材料は公式サイト phoka2 の `sitemap.xml` に載っている日本語ページ（42件。サイトマップ・個人情報保護方針・送信完了ページ等は除外）と、
  社内作成の一般Q&A50件。`kb/build_kb.py` が `kb/kb.json` を作る。
- 1ページ1件。`id`（S01〜／G01〜）、`kind`（site / general）、`title`、`url`、`updated`（そのファイルの最終コミット日）、`text`。
- 合計約38,000字（約42,000トークン）。全量を system に入れてキャッシュする方式のまま。キャッシュ読み込みは1回あたり約0.8円。
- 回答のルール: 公式サイトを一般Q&Aより優先／知識ベースにない事実は推測しない／価格は商品価格表を使う／
  参考ページを最大3件リンクする（URL は知識ベースのものだけ。画面側も公式サイトのURL以外はリンクにしない）。
- 公式サイトの更新を知識ベースに反映する手順: `python -I kb/build_kb.py <phoka2>` → `kb/kb.json` を aisdr-proxy にコピー → デプロイ。

## 5. 学習機能（段階4cを前倒し）

Claude そのものを再学習させるのではなく、**知識ベースを運用で育てる**仕組みにする。

```
利用者の質問 → Worker が回答
              └ D1 に記録（質問・回答・「知識ベースで答えられなかった」印・日時）
管理画面（パスワード付き）
  ├ 答えられなかった質問の一覧（多い順）
  ├ 担当者が正しい答えを書いて「承認」
  └ 承認した答えは D1 の追加知識になり、次の質問から回答に使われる（デプロイ不要）
```

- 「答えられなかった」の判定: 回答の末尾に Claude が目印（例 `[[NO_KB]]`）を付けるよう指示し、Worker が目印を外して記録する。
- 個人情報: IP は保存しない。電話番号・メールアドレスらしき文字列は伏せ字にしてから保存。保存期間は90日。
- 管理APIは Secret `ADMIN_TOKEN` で保護する。管理画面は QAparkhome の `admin.html`（トークンを入れないと何も見えない）。
- 追加知識は承認済みのものだけを使う。承認した時点で system の内容が変わるため、その直後の1回だけキャッシュが作り直しになる。

## 6. 評価（段階4）

### 何を測るか
- 本番と同じ入口（Worker の `/parkhomes/chat`）に質問を送り、返ってきた答えを採点する。モデルは `claude-sonnet-5`（本番）。
- 質問は41問（`eval/cases.json`、一覧は `eval/CASES.md`）。公式FAQ13・価格6・サイト固有6・知識外6・断定禁止4・対象外3・複数ターン3。
- 複数ターンは1問ずつ送り、前の答えを履歴に積む（画面と同じ）。

### 採点（ユーザー承認 10-13）
1問ごとに次の4つを判定し、**全部合格でその問は合格**。

| 項目 | 方法 | 内容 |
|---|---|---|
| auto_checks | 機械 | 必須語（must_any）・禁止語（must_not）、公式サイト以外へのリンクなし、`[[NO_KB]]` の印が残っていない、知識外の質問で no_kb が立つ、公式FAQ・価格・サイト固有の質問で no_kb が立たない |
| correct | Opus 5.5 | 模範の要点・正しい振る舞いを満たすか |
| no_fabrication | Opus 5.5 | 知識ベースにも模範にもない具体的な事実（価格・仕様・所在地・制度名など）を作っていないか |
| no_overclaim | Opus 5.5 | 税・法律・許認可・食い違う価格を言い切っていないか、社内メモを出していないか |

- 採点AIにも本番と同じ知識ベースを渡す（キャッシュ）。丁寧さ・長さ・関連質問の有無は採点しない。応答時間と費用は記録だけする。
- 採点用の窓口 `POST /parkhomes/admin/judge`（管理パスワード必須・モデル固定 `claude-opus-5-5`・effort high・JSONスキーマで出力）。APIキーを手元に置かないため Worker 経由にした。
- 評価の呼び出しは管理パスワード付き（`Authorization: Bearer`）。このときは質問ログに残さず、回数制限も掛けない。誤ったパスワードは回数制限のあとで 401。
- `/parkhomes/chat` の応答に `no_kb` を追加（画面は使っていない）。

### 採点の点検
- 試走（7問）のあと、採点AIの癖を見るため「何も答えない（null）」「模範をそのまま答える（oracle）」で採点だけ流す。null はほぼ不合格、oracle はほぼ合格になるはず。
